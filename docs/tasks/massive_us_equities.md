# Massive 美股数据任务

通过 `MASSIVE_KEY` 接入 Massive（原 Polygon）的 Stocks REST API，供美股市场广度和实际波动率研究使用。任务会被统一 factory 自动发现，GUI 的数据源筛选项为 `massive`，业务域为 `stock`。

| 任务 | 源表 / 同名 rawdata 视图 | 内容和业务键 |
|---|---|---|
| `massive_stock_us_basic` | `massive.stock_us_basic` | 活跃的美国交易所上市证券资料，保留证券类型、交易所、FIGI；键为 `ticker, snapshot_date` |
| `massive_stock_us_daily` | `massive.stock_us_daily` | 全市场未复权 OHLCV、VWAP、成交笔数；键为 `ticker, trade_date` |
| `massive_stock_us_split` | `massive.stock_us_split` | 拆股、并股、送股事件及每次事件的股数比例；键为 `event_id` |

## 安装和首次建表

1. 安装可选依赖：`python -m pip install -e ".[massive]"`。交易日历使用 `exchange-calendars` 的 XNYS，不套用 A 股交易日历；Windows 使用 `tzdata`。
2. 设置 `MASSIVE_KEY` 环境变量。客户端运行时读取；Windows 也会在进程变量不存在时读取系统/用户环境变量，因此任务发现不要求事先有密钥。密钥仅放入认证请求头，不进入 URL、日志或配置示例。
3. 核对目标数据库及 `stock_us_*` 是否已存在，单独执行 `scripts/database/massive_us_schema.sql`。这是三张新源表和三张 rawdata 视图的显式迁移；普通任务只验证映射，不自行修复 rawdata。
4. 重新启动 GUI，在 `massive` 数据源下选择任务。所有任务支持统一 SMART / MANUAL / FULL 执行路径，无需新增 GUI 控件。

## 日期范围与更新

- 免费版默认限制为滚动两年。为避免边界时刻落在权限之外，自动起点是 UTC 当日减两年再加一天。手动范围早于该边界会直接报错；`history_years` 仅应在实际账户权限允许时调整。
- 截止日不超过**纽约日期的前一个自然日所对应的最近交易日**。即使美东当日已到 16:00，也不会抓尚未结束的当前日。节假日和周末由 XNYS 排除；半日市仍作为完整交易日。
- 日线首次 SMART 只抓最近 7 个自然日；之后从库内最新日回看 3 个自然日，覆盖晚到修订。FULL 按权限窗口从早到晚回填约两年，每个交易日一次请求。按 13 秒请求间隔，首次日线 FULL 预计约两小时，取决于网络和实际交易日数。
- 证券资料首次 SMART 和 FULL 均抓**最近完整交易日的完整证券快照**。后续 SMART 从已有最新快照日补到截止日。回补历史股票池需使用 MANUAL 指定日期窗口；每一天均独立请求当日证券池并完整翻页，不能用今天的名单替代历史名单。
- 拆股事件首次 SMART 回看 30 个自然日，此后回看最近事件日之前 30 天；FULL 拉取整个配置历史窗口。事件表按 ID UPSERT，保存源事件比例，不保存会因未来拆股变化的累计复权因子。
- 默认所有模式均逐批处理、验证、入库，避免将两年全市场日线堆入内存。日线/证券快照按完整日期原子替换，重跑能移除源方从同日快照撤回的证券；不改变其他日期。
- 单任务固定串行且失败即停。此前完整日期可能已提交，失败日和之后的日期不会推进；可重跑同一窗口。取消和分页失败不得保存半份证券快照。不要启用 INSERT-only 模式。
- 三个任务共享同一进程、同一密钥的限速，最短请求间隔 13 秒。多进程运行仍共享服务商账户额度，应避免同时用多个采集进程；429 按退避重试，401/403 不重试。官方套餐/权限变更仍会明确失败。

## 字段和研究口径

- `ticker` 保存原代码，例如 `BRK.B`，不改造成 A 股 `ts_code`。行情覆盖普通股、ETF、ADR、优先股等上市证券，不包含 OTC。用于普通股广度时，应按同日 `stock_us_basic.security_type = 'CS'` 筛选；ADR（例如 `ADRC`）和 ETF 单独统计。
- 历史证券资料中，个别已上市证券的类型字段可能缺失；保留这些证券并显式标为 `UNKNOWN`，不根据名称推断类型，也不混入 `CS`。回补回执和最终审计单独报告其数量；如果整份响应缺少类型字段，仍判为接口结构异常。
- 原始价格按供应商报价币种保留，成交量单位为股，允许小数股数。不套用 A 股的手/千元单位转换，不将 `VWAP × volume` 冒充准确成交额。
- `adjusted` 固定为 `false`。不能直接用跨拆股的原始收盘价计算涨跌幅、均线或波动率。针对日期 D 到目标基准日 B 的价格复权，应乘以期间各次事件的 `split_from / split_to`，只纳入 `D < execution_date <= B` 的事件。事件缺失或价格窗口超出事件覆盖时，不能宣称复权完整。
- 本次未采集现金分红，拆股复权价格不等于含分红总回报。Massive 日线沿用供应商聚合和成交条件规则，不能未经对照就把全部 OHLCV 字段解释为严格 09:30—16:00 的交易所官方口径。
- `snapshot_date` / `trade_date` / `execution_date` 是业务日期；`observed_at` 是本机实际获取该批数据的 UTC 时间。历史查询返回的分类、公司名或拆股修订不能据此证明历史时点已知。回测和次日开盘执行需要另外核验数据实际可得时间。
- 供应商 `last_updated_utc` 转为 `source_updated_at`，显式截取到 PostgreSQL 的微秒精度。
- `stock_us_basic` 保存活跃证券池，不是全部退市证券的主档。历史日期查询可获得供应商记录的当日活跃证券，但需要核验退市、更名和分类覆盖。证券快照与行情还应按同日代码集合做覆盖对账，不能把行情缺失当作上涨或下跌。
- 全市场日线和证券快照默认至少 1,000 条；响应条数、业务键、日期、必要数值、OHLC 关系异常时整体拒绝保存。该门槛只能拦截明显空缺，不是全市场完整性证明。

## 历史回补与断点续跑

专用入口 `scripts/production/backfill_massive_us.py` 按交易日核对缺口，适用于库内已经有最新日期、但早期历史尚未入库的情况。SMART 的最大日期不能代表历史已齐全。

先生成只读计划（默认采用运行当日允许的两年窗口）：

```powershell
python scripts/production/backfill_massive_us.py --run-dir logs/massive_us_backfill_YYYYMMDD
```

读取输出的 `plan_hash` 后，执行同一计划；中断后使用相同命令续跑：

```powershell
python scripts/production/backfill_massive_us.py --run-dir logs/massive_us_backfill_YYYYMMDD --execute --expected-plan-hash <plan_hash>
```

执行程序验证源表、rawdata 映射、数据库指纹、代码哈希和磁盘余量，备份三张目标表，再依次回补拆股事件、最早缺失日的证券快照、全部缺失日线和其余历史证券快照。所有请求在同一进程串行限速；不要同时从 GUI 或另一进程运行 Massive 采集。

- `plan.json`：冻结的日期、499 日等实际计划数量、代码哈希、执行前覆盖和数据库指纹。
- `backup_manifest.json` / `before_*.csv.gz`：执行前目标表备份及校验和。
- `status.json`：每 30 秒刷新存活时间、PID、当前阶段及日线/证券快照已覆盖日数。`running` 仅表示进行中，`failed` 表示需要处理记录的错误。
- `receipts.jsonl`：完整入库后逐批追加的任务结果及独立行数核对。
- `audit.json`：全部采集后独立核查缺失交易日、重复键、数值异常、源表与视图行数、普通股行情覆盖及窗口外数据是否变化。只有审计通过才写入 `status=completed`。

权限窗口仍按真实运行时间检查；如果长期中断导致最早缺口超出滚动两年权限，程序会明确失败，不能把该日期跳过后标记完成。后续新交易日不自动并入已经冻结的回补计划，完成后再走日常 SMART 更新。

判断后台进程仍在运行时，应同时核对 `updated_at` 持续刷新且对应 PID 存活；强制结束进程或重启电脑可能留下旧的 `running` 状态。

### 网络中断后的自动续跑

Windows 长时间后台回补可使用守护入口，继续同一份冻结计划：

```powershell
python scripts/production/supervise_massive_us_backfill.py --run-dir logs/massive_us_backfill_YYYYMMDD --expected-plan-hash <plan_hash>
```

守护程序串行启动原采集器，保留所有已入库日期及原有日志。仅对本次进程新记录的网络故障、HTTP 429 和 HTTP 5xx 退避重试；无新进展时最多重试 6 次，等待时间依次为 1、3、10、30、60、60 分钟。401/403、权限窗口、计划变化和数据校验异常仍立即停止，旧失败状态不会被当成新一次网络故障。恢复过程继续核验原计划哈希、数据库指纹和备份，不能跳过失败日期。

`supervisor.json` 记录守护进程、采集子进程、重试次数及下次尝试时间。`backoff` 表示等待重试，此时 `status.json` 会保留刚刚失败的采集结果；`supervisor.json` 和 `status.json` 均为 `completed` 才表示整个流程完成。相同运行目录由文件锁阻止重复守护，数据库锁进一步阻止并行回补。
