# 架构审查整改：恢复范围与可信提交

本轮针对 2026-09-22 架构审查中的错误成功、恢复缺口和入口漂移实施修复。保留 PostgreSQL、领域协调器、现有公式、GUI/CLI 和 FundPos 冻结运行时。代码合同与生产采用分开记录；代码完成本身不证明某个数据产品已经迁移或历史数据已经修复。

## 已实现的行为

| 审查项 | 行为与证据 | 保证的边界 |
|---|---|---|
| F1：PIT 没有自己的增量水位 | `pit.task_run` 由正式协调器在写入前记录，在任务完成后记录结果。日区间增量必须有从声明历史起点建立的成功全量基线；来源检查异常阻断。恢复从前次覆盖终点及旧来源修订向前扩展。手工切片、失败、取消和空全量结果不建立基线。 | 水位使用前次批次开始时间并回看一天；不能证明供应商数据的历史可得性。来源必须可靠维护更新字段。 |
| F2：同批次下游少一个月 | 月度计划把本批次上游承诺完成的月份纳入依赖边界；财务子任务的日区间包含本批次上游修订范围。运行结果必须覆盖计划月份。 | 冻结的是目标范围，不是历史源快照。依赖缺失或质量失败仍阻断，不能把“规划到了”当成“计算完成”。 |
| F3：原子替换不等于可发布 | 月度 PIT 拒绝未说明原因的空月份或漏月。SQL/Python Features 暂存及注册 MV 在同一事务内执行声明的空值、必需键和行数变化检查；失败回滚。`stock_daily_enriched` 额外校验源合格业务键集合。 | `grain`、经济含义、覆盖率等描述性元数据仍只作说明，结果列出 `advisory_keys`。没有给每个配方伪造完整实体分母。 |
| F4：滚动窗口留下历史缺口 | 六个增量配方声明来源日期/更新字段；`features.refresh_checkpoint` 与产物同事务提交。停更和旧日修订扩展补算范围；超过 120 个日历日、无日期来源变化、检测到行数下降或缺失更新时戳要求显式全量回补。来源/键/日期合同或公式版本变化要求新基线。 | 六个配方见下文。检查点表示按现有来源重建过的范围，不认证源完整性；净行数不能识别被新增抵消的删除。 |
| F5：读取参数与数据语义不符 | 股票价格默认及支持值为 `adjust=False`，请求复权明确拒绝；支持的 `fields` 实际投影。行业仅支持 `stock_basic` 当前标签，SW 分类请求明确拒绝。返回属性说明价格和行业语义。 | 没有实现复权算法或 PIT 行业读取；需要这些语义的消费者应显式选其他来源。 |
| F6：rawdata 映射失败被当作成功 | 日常任务仅验证精确来源和列投影，缺失、错误来源、过滤条件或列顺序不符均失败；不在普通采集里修视图。Tinysoft 转债保留显式兼容列序。 | 新增采集表或源表增列需要维护映射；纯 SQL 生成器不自动决定多供应商优先级。 |
| F7：候选变更后技术产品仍旧 | GUI 月度候选成功或已成功重试后刷新候选宇宙技术 MV；下游失败返回部分成功，可重试而不重复候选 AI 调用。只有当前候选没有跟踪指数时，空 MV 才有显式理由。 | 范围是 GUI 正式日常链。直接调用低层候选维护函数的外部消费者仍须安排下游刷新。 |
| F8/F9：本机入口与凭据 | 本机已禁用指向缺失脚本的 `AlphaHome-ETF-Candidate-AI-Monthly`，未启用新的调度；Git origin 已去除 URL 用户信息。 | 这是本机状态，不随 Git checkout 自动传播；未验证或撤销远端凭据。 |

六个增量样板：`stock_daily_enriched`、`stock_sma_daily`、`dc_index_features_daily`、`industry_toplist_signal_daily`、`market_sentiment_daily`、`market_technical_daily`。其他普通表使用显式 full，或先实现来源恢复合同；不能静默退回仅刷新最近 30 天。

PIT 批次新增跨进程运行锁；并行任务取消时先等待其余写入结束再释放锁。月度目标替换也持有事务锁。硬崩溃可能留下 `running` 账本行，下一次运行保守重放；不把该行当作成功。PIT 数据提交和结果账本是两个事务，故提交后失联可能重算，不能提供 exactly-once 承诺。Features 检查点与目标在同一事务，质量失败不推进检查点。

## 生产采用顺序

以下是通用生产切换顺序。2026-09-22 已按该顺序完成恢复账本安装和 `stock_daily_enriched` 纵向样板迁移，结果见“生产采用记录”；其他 Features 配方和 PIT 产品仍需逐项执行，不能由样板结果推定已经迁移。

1. **安装恢复表。** 在已有 PIT/Features 部署上运行 `python -m alphahome.common.maintenance_sql recovery-ledgers` 生成 SQL，审阅后针对明确数据库执行。它只新增两个账本及索引，不填充、认证或重写旧产物。已有初始化入口也包含这些 DDL。常规运行缺表会报 `migration_required`。
2. **核对 rawdata 映射。** 对预检或采集返回的精确目标，使用 `python -m alphahome.common.maintenance_sql rawdata-mapping --view stock_daily --source-schema tushare --source-table stock_daily` 生成单对象 SQL。特殊列序用重复的 `--column` 指定。先检查供应商优先级、原列序、类型、权限和依赖；`OR REPLACE` 不兼容时停止，禁止用 `DROP CASCADE` 强推。若目标是必须保留的旧实体表，可显式增加 `--archive-existing-table <归档名>`，在同一事务中先重命名归档再建视图；归档名冲突时整笔迁移回滚。
3. **选择纵向产品并建立基线。** 财务 PIT 先从管理器声明的历史起点执行 full_backfill，再运行增量；手工局部回填不替代这一步。行情 Features 对选中的配方执行 full 到明确截止日，再核对范围、业务键和新账本。使用现有 dry-run/plan_hash 入口冻结并核验执行计划，保存产物对照。不要直接把旧“最近成功时间”插入账本。
4. **验收恢复而非只验收成功码。** 对样板核对停更 60 天后没有应有日期缺口；修订旧日期后该日期确实变化；上下游同批次到达新月；非空但漏键的结果拒绝发布；失败保留旧数据与旧水位。确定真实源的空值/行数阈值适用，门禁失败时查原因而不是关闭检查。
5. **切换日常入口。** GUI 月度候选链观察到候选维护和后续 MV 两个结果都合格再视为完成。盘点所有外部计划任务、固定解释器和调用者；新入口验证通过后再启用对应调度。需要撤销旧远端凭据时，在其所属平台处理，不在报告或 URL 中复制凭据。

若历史月份本来就没有合格样本，月度管理器须根据实际来源、业务日期和分母向 `_atomic_replace_months(expected_empty_months={month: reason})` 提供逐月理由。当前没有为所有历史起始月份预置这种证明；遇到它会保守停止，需要针对产品补充证据。不能写一个无条件空理由来通过验收。

## 兼容性与回退

- 未建立基线的旧部署会被阻断。这是预期行为，部署时应先安排全量成本和验收窗口。超过恢复预算也不自动启动大型全库任务。
- `row_count_change` 按已有声明的相对变化阈值执行；普通表只比较既有日期范围，追赶时新日期的正常增长不计入异常变化。已有日期的大规模合法扩容、迁移或删除仍可能触发。修改阈值属于配方合同调整，需要依据与重新验收。
- 旧目标只有局部历史而首次 full 会合法扩容时，必须单任务、显式 full，并在预览和执行两次都使用 `--approve-initial-baseline-growth`。计划会冻结来源业务键的精确预期行数；执行仍要求双向业务键集合一致，且授权只允许首次基线的增长，不能允许缩减、空结果、重复键或已有检查点后的再次越界。不要通过放大通用阈值或手工插入检查点绕过。
- 计算公式改变后，维护者必须增加 `recovery_contract_version`，再建立新全量基线；仅变更实现文件不能推断历史结果已经更新。
- 来源检查目前会统计声明来源的行数并检查更新日期，可能扫描大表；`stock_daily_enriched` 已完成真实生产测量，不能将其耗时、索引效果或门禁阈值外推到其他配方。保留预检超时和恢复预算，按纵向产品逐项测量再扩大运行范围。
- 回退代码不会自动删除新账本或恢复源数据。数据库变更和产物回滚应按目标范围另行审阅；失败后先查已提交单元，避免回滚覆盖后续正确输出。
- PIT/Features 仍明确返回 `source_consumption=unverified`；没有将重建产物升级为前瞻可用、资金或订单权限。FundPos 仍保持 check/shadow 边界。
