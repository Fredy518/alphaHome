## 演练发现的入口风险

`ConfigManager` 仅在配置文件没有数据库 URL 时才读取 `DATABASE_URL`。因此本阶段一次 Factors `schema --apply` 试跑实际连到了本机 `alphadb`，没有落到预设的隔离库。该 SQL 只有 `CREATE ... IF NOT EXISTS`；命令执行前后均报告结构就绪，12 个目标表/索引的目录行事务年龄均为旧值，未发现新建对象或业务数据改动。后续立刻停用该方式，并让 Factors CLI 与 Features CLI 一样优先使用显式 `ALPHAHOME_DATABASE_URL`。空白隔离库的只读 `schema` 检查报告五张表缺失，验证了新的目标选择。生产维护前仍要独立核对数据库主机、端口、库名及角色，不能只设置 `DATABASE_URL`。

## 尚未满足的生产迁移门槛

1. **整库恢复证明。** NAS 数据库约 130.8 GB；本机 C、D、E 各盘可用空间均不足 100 GB。X、Y 盘虽有空间，但均映射到数据库所在的同一台 NAS `192.168.5.6`，不能充当独立故障域的备份或恢复场地。本次只有结构和相关表的选择性恢复，没有完成真实 NAS 整库备份及独立恢复，也没有验证恢复后的 owner、ACL、角色与服务配置。须在容量足够的独立目标完成，不能用 `pg_restore --list` 或本次演练替代。
2. **生产停写与发布版本。** 另一台电脑的实际 `HEAD`、调度器状态和在途任务未核对。数据库迁移前必须暂停受影响写入，确认无在途任务，并固定应用发布提交；当前恢复分支的代码不能因另一台电脑“看到了分支”就视为已部署到 `main`。
3. **数据产品验收。** 四个物化视图本次只创建、未在 NAS 按真实来源刷新；两张 All-A 表在隔离库使用本机历史数据，不能代表 NAS 重算结果。其他五个增量 Features 基线、PIT 产品及来源实际可得时间仍需按各自合同验收。`source_consumption=unverified` 不因结构迁移而消失。
4. **历史证据可携带性。** FundPos 数据库记录中的本机绝对路径需在另一台电脑上可访问或迁移后显式重映射；AI/人工候选决定与 Factors 修复归档不能通过重新运行任务代替。迁移前需冻结来源快照、按业务键对账并保留原始证据文件。

## 正式迁移顺序

在上述门槛满足后，由本机在维护窗口执行：先备份并验证恢复点；然后修正四张既有 Features 表的键约束，安装 Factors 治理及归档结构、独立 Features、ETF 候选池和 FundPos；再分域导入不可重生历史，按 NAS 来源重建派生数据并核对内容与权限。NAS 验收后才将配套代码发布到远端 `main`，另一台电脑按准确提交拉取、逐域恢复任务并观察首次自然运行。`scripts/database/alphadb_nas_logical_sync.py` 的本机发布者到 NAS 订阅者路径不用于这一迁移。

Y 盘整库归档及仍待完成的独立实例恢复验收，见 [NAS 第三阶段备份记录](nas-stage3-backup-20260925.md)。
